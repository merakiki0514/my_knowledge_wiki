# Concept Reference

이 문서는 위임하지 않고 직접 이해하기 위한 참고 자료다. 지금까지 실행한 것(Phase 0~1)과 앞으로
실행할 것(Phase 2~6, `RESEARCH_GUIDEBOOK.md` 참조)에서 등장하는 기술적·개념적 요소를, "왜 이
프로젝트에서 중요한가"를 붙여서 정리했다. 실제로 관측된 것은 구체적 근거(`07.wiki` 문서, 실험
run id)를 함께 적었다 — 일반론이 아니라 이 프로젝트에서 실제로 일어난 일이다.

## 이 문서 사용법

- 개념 자체가 궁금하면 해당 절만 읽는다. 순서대로 읽을 필요 없다.
- "왜 중요한가"는 이 프로젝트 맥락에서의 의미이지, 일반적인 정의의 전부가 아니다.
- 더 깊은 원본은 각 절 끝의 `Related`에 링크해뒀다.

# A. 지금까지 실행한 것에서 나온 개념 (Phase 0~1, exp_001)

## A1. Reasoning 모델과 Thinking Block

`deepseek-r1:14b`는 최종 답을 내기 전에 내부적으로 긴 사고 과정(chain-of-thought)을 먼저
생성하고, 이를 별도의 "thinking block"으로 노출하는 계열의 모델이다(추론 능력을 강화학습으로
훈련한 "reasoning model"). 이 방식은 답변 품질을 올려주지만 대가도 있다 — 이 모델은 간헐적으로
thinking block **안에서** 종료 토큰(EOS)을 내보내고, 최종 답변(`response`) 없이 턴을 끝내버린다.
HTTP 요청 자체는 성공하기 때문에 겉보기엔 정상 응답처럼 보인다.

**왜 중요한가**: 이 조기 종료를 "응답이 문장부호로 끝나는가" 같은 휴리스틱으로 판정하려다 오탐이
났다(참고문헌 목록으로 정상 종료된 응답을 미완결로 오분류). 최종적으로는 Ollama API가 제공하는
`done` 불리언 필드를 신뢰하는 것으로 교체했다. **모델 응답의 형태를 추론해서 대체 신호를 만들기
전에, API가 이미 제공하는 명시적 상태 필드가 있는지부터 확인해야 한다**는 일반적 교훈이기도 하다.

- Related: `07.wiki/methodology/thinking-model-completion-signal.md`, `06.scripts/ollama_client.py`

## A2. Temperature / Seed와 재현성의 한계

`temperature`는 다음 토큰을 고를 때의 무작위성 정도(0이면 항상 최고 확률 토큰만 선택), `seed`는
그 무작위성 생성기의 초기값이다. 이론적으로 `temperature=0` + 고정 `seed`면 같은 입력에 항상 같은
출력이 나와야 한다.

실제로는 그렇지 않았다. 동일 문항 30개를 두 차례 실행했더니 응답 길이가 문항별로 최대 1,253자
차이 났고, 한 문항은 정답에서 오답으로 바뀌었다. 원인은 llama.cpp/Ollama의 **prompt
cache**다 — 여러 문항이 공유하는 시스템 프롬프트 접두부가 캐시에 있는지 여부에 따라 GPU
부동소수점 연산 순서가 미세하게 달라지고, 부동소수점 연산은 결합법칙이 성립하지 않으므로 이 차이가
토큰 하나를 뒤집으면 그 이후 문장 전체가 달라진다. 이는 우리 코드의 버그가 아니라 추론 서버의
성능 최적화(캐싱, 배칭)와 결정성 사이의 구조적 트레이드오프다.

**왜 중요한가**: **단일 실행 결과를 확정값으로 다루면 안 된다.** 이후 모든 실험은 문항당 최소
3회 반복 실행하고 변동 폭을 함께 보고하도록 설계 원칙에 반영했다.

- Related: `07.wiki/methodology/ollama-prompt-cache-nondeterminism.md`

## A3. 환각(Hallucination) — 정확도와는 다른 축

환각은 "그럴듯하지만 사실이 아닌 내용을 생성하는 것"이다. 이 프로젝트에서 중요한 것은 환각이
단일한 현상이 아니라 **최소 세 가지 서로 다른 하위 패턴**으로 관측되었다는 점이다.

1. **결론은 맞지만 근거가 전부 허위** — "IDS 설치는 의무가 아니다"는 정답을 내면서, 근거로 든
   조항·문서(`IMO Resolution MSC.423(98)` 등)는 존재하지 않았다. 정확도만 측정하면 이 응답은
   "정답"으로 집계되지만, 모델이 실제로 알아서 답한 게 아니라 그럴듯한 근거를 사후에 갖다 붙였을
   가능성을 보여준다. **이것이 이 프로젝트가 정확도와 환각을 독립 지표로 분리해 측정하는 이유다.**
2. **유보 표현을 붙이고도 창작한다** — "확정할 수 없으나 일반적으로..."라고 말한 직후에 존재하지
   않는 구체적 조항 내용을 만들어낸다. 프롬프트에 "확실하지 않으면 추측하지 말라"는 지시를
   명시적으로 넣었는데도 발생했다. 즉 **"불확실성을 말로 표현하는 능력"과 "표현하면서 실제로
   창작하지 않는 능력"은 별개**다.
3. **허위 인용은 해사 도메인 고유 문제가 아니다** — 일반 사이버보안 대조군 문항(NIST CSF 질문
   등)에서도 같은 성격의 허위 인용이 나왔다. 즉 인용 조작은 모델의 **일반적인 습성**이고, 해사
   도메인에서는 그 위에 도메인 사실 부족까지 겹쳐서 실패가 더 심하게 나타나는 구조다. 이 발견이
   exp_001의 해석 축을 "일반 지식 대 해사 지식"에서 "개념 설명 대 검증 가능한 사실·출처"로
   바꿨다.

**왜 중요한가**: 이 세 패턴 모두 "정확도가 몇 %인가"만 보는 평가로는 잡히지 않는다. `exp_002`
(RAG)와 `exp_003`(hallucination)의 평가 지표 설계가 이 관측 위에 서 있다.

- Related: `07.wiki/model_behavior/correct-conclusion-fabricated-evidence.md`,
  `hallucination-despite-hedging.md`, `cross-domain-false-citation.md`

## A4. 약어 오독과 도메인 용어의 취약성

`IACS`(International Association of Classification Societies, 국제선급협회)를 `Industrial
Automation and Control Systems`, `국제 해사기구`(IMO와 혼동), `해사기계장치협회` 등으로 서로 다르게
잘못 풀어썼다. `CBS`(Computer Based System)도 `Cybersecurity Baseline Specifications`로
오확장했다. 정확한 확장이 나온 것은 30문항 중 단 2회.

**왜 중요한가**: 이 프로젝트의 규정 지식은 거의 전부 `IACS`와 `CBS`라는 두 용어를 중심으로
조직되어 있다. 이 두 약어를 잘못 풀면 답변 전체가 잘못된 프레임(예: IEC 62443 자산소유자
프로그램)으로 흘러간다 — 개별 조항 오류보다 상위 수준의 실패다. 프롬프트에 용어집을 주입하는
것만으로 교정되는지가 저비용으로 확인해볼 만한 다음 과제로 남아 있다.

- Related: `07.wiki/model_behavior/abbreviation-misreading.md`,
  `ur-e26-fire-safety-misconception.md` (UR E26을 화재안전 규정으로 오인한 사례 — 같은 성격의
  상위 수준 실패)

## A5. 다국어 토큰 누출

한국어로 묻고 한국어로 답하는 응답 안에 중국어·일본어 단어가 문법적으로 자연스러운 위치에
섞여 나왔다(오탈자가 아님). 또한 질문은 한국어인데 응답 전체가 영어로 나온 경우도 다수였다.

**왜 중요한가**: 응답 언어 자체가 통제되지 않은 변수라서, 실패가 "도메인 지식 부족" 때문인지
"한국어 처리 자체의 불안정성" 때문인지 분리되지 않는다. 후속 실험에서 같은 문항의 영문판을
병행해야 하는 이유다. 정규식/키워드 매칭 기반 자동 채점을 만들 때도 이 현상을 감안해야 한다.

- Related: `07.wiki/model_behavior/multilingual-token-leakage.md`

## A6. 평가 방법론 — 함정 문항, 전문 채점, 채점 기준서

- **함정 문항(trap question)**: 정답이 "모른다/근거 없다"인 문항을 의도적으로 섞어, 모델이
  없는 근거를 지어내는지 확인하는 설계. H2(환각 가설)를 검증하는 핵심 도구다.
- **응답을 잘라서 채점하면 안 된다**: 500~900자만 보고 초벌 채점했다가, 전문을 다시 읽자 허위
  인용 4건을 추가로 발견했다(15/30 → 19/30 환각 문항). 허위 인용은 답변 **말미**의 "참고 문헌",
  "관련 규정" 절에 몰리는 경향이 있었다 — 본문은 무난하게 쓰고 마지막에 근거를 지어내는 형태다.
  "없는 것을 찾는" 채점은 안 읽은 부분의 문제를 아예 인지하지 못하게 되므로, 요약·절단 없이 전문을
  봐야 한다는 원칙이 채점 기준서 1번으로 명시됐다.
- **rubric(채점 기준서)**: 무엇을 정답/부분정답/오답/환각으로 볼지 사전에 정의한 문서
  (`exp_001_baseline/01.config/rubric_v1.md`). 채점자(사람이든 향후 LLM-as-judge든)의 판단
  일관성을 위해 필요하다.

**왜 중요한가**: 앞으로 문항 수가 늘면 사람이 매번 전문을 읽는 비용이 커져 자동 채점(LLM을
채점자로 쓰는 LLM-as-judge)을 도입하게 될 텐데, 그때도 "요약된 입력으로 채점하는" 같은 함정에
빠지지 않도록 설계 단계에서 반영해야 한다.

- Related: `07.wiki/methodology/score-full-response-not-truncated.md`

## A7. IACS UR E26 / E27과 "규정 버전"이라는 개념

`IACS`(국제선급협회)는 각 선급이 공통으로 적용할 최소 요구사항을 `UR`(Unified Requirement)이라는
형태로 발행한다. `UR E26`은 선박 전체의 사이버 복원력(Cyber resilience of ships), `UR E27`은
개별 탑재 장비의 사이버 복원력을 다룬다. 두 문서가 "선박 = Zones & Conduits로 나뉜 하나의 시스템"
이라는 관점을 요구한다는 점에서 Model 01의 Threat Modeling/Defense Guide 설계의 직접적 근거다.

**왜 중요한가**: exp_001에서 모델이 `UR E26`의 2022년판이 **철회되었다는 사실을 인지하지
못했다**(H3, 판본 혼동). 규정은 한 번 학습되면 고정된 텍스트가 아니라, 개정·철회를 거치며
버전이 바뀌는 살아있는 문서라는 점 — 그리고 LLM은 학습 시점의 스냅샷만 알고 있어 최신 버전 정보를
따로 주입하지 않으면 구버전을 최신인 것처럼 답한다는 점 — 이 이 프로젝트가 Knowledge Engine에
버전 메타데이터를 반드시 포함해야 하는 이유다.

- Related: `01.knowledge/01.regulations/iacs/UR E26.md`, `RESEARCH_STATE.md`의 H3

# B. 앞으로 쓰일 개념 (Phase 2~6)

## B1. RAG (Retrieval-Augmented Generation)

모델이 사전학습 때 외운 지식(parametric memory)에만 의존하지 않고, 질의 시점에 외부 문서에서
관련 있는 조각(chunk)을 검색해 프롬프트에 끼워 넣은 뒤 그것을 근거로 답하게 하는 방식이다. 보통
① 문서를 chunk로 자르고 → ② 각 chunk를 벡터(embedding)로 변환해 저장하고 → ③ 질문이 오면 가장
유사한 chunk를 검색(retrieval)해서 → ④ 프롬프트에 주입하는 순서로 동작한다.

**왜 중요한가**: `exp_002_rag`의 핵심 질문은 "RAG가 정확도는 올리는가, 그리고 허위 인용도 같이
줄이는가"다(가설 H4는 "정확도는 오르되 허위 인용은 비례해서 줄지 않는다"). A3의 관측(허위 인용은
일반적 습성)을 고려하면, 검색된 진짜 근거가 있어도 모델이 그 위에 또 다른 창작을 얹을 가능성이
있다 — RAG를 "환각을 자동으로 없애는 장치"로 오해하면 안 되는 이유다.

- Related: `05.experiments/exp_002_rag/PLAN.md`, `07.wiki/model_behavior/cross-domain-false-citation.md`의 Open Question

## B2. Grounding / 근거 인용 강제

RAG가 "관련 문서를 찾아주는 것"이라면, grounding은 한 단계 더 나아가 **모델의 모든 주장에
검증 가능한 출처를 강제로 붙이게 만드는 것**이다. 예: "이 네트워크 구간에는 방화벽이 필요하다"가
아니라 "IACS UR E26 §6.4에 근거하여 이 네트워크 구간에는 방화벽이 필요하다"처럼, 결론과 근거를
분리해서 요구하고 근거 부분을 검증한다.

**왜 중요한가**: Model 01 아키텍처의 "Hallucination Grounding Layer"가 바로 이 개념이다.
RAG(B1)가 올바른 문서를 찾아주는 것과, 모델이 실제로 그 문서를 근거로 답했다고 검증하는 것은
다른 문제다 — A3-1(결론은 맞는데 근거는 허위)이 정확히 이 둘의 간극에서 발생했다.

- Related: `00.docs/02.architecture/model_01_architecture.md`, `05.experiments/exp_003_hallucination/PLAN.md`

## B3. STRIDE 위협 모델링

마이크로소프트가 제안한 위협 분류 체계로, 시스템의 각 구성요소에 대해 아래 6가지 위협 유형을
빠짐없이 점검하도록 돕는 체크리스트다.

| 약자 | 위협 유형 | 예시(선박 맥락) |
|---|---|---|
| S | Spoofing (신원 위장) | GPS/AIS 신호 스푸핑으로 가짜 위치 주입 |
| T | Tampering (변조) | NMEA 메시지를 가로채 항로 데이터 조작 |
| R | Repudiation (부인) | 누가 방화벽 설정을 바꿨는지 로그로 추적 불가 |
| I | Information Disclosure (정보 노출) | VSAT 통신을 도청해 항로/화물 정보 유출 |
| D | Denial of Service (서비스 거부) | ECDIS에 과도한 트래픽을 보내 항해 정보 표시 지연 |
| E | Elevation of Privilege (권한 상승) | 엔지니어 계정으로 접근해 Engine Control까지 제어 |

**왜 중요한가**: `exp_004_threat_modeling`의 핵심 방법론이다. "위협이 뭐가 있을까"를 즉흥적으로
브레인스토밍하는 대신, 자산 하나하나에 STRIDE 6개 항목을 체계적으로 대입해 빠짐없이 확인하게
만든다 — LLM에게 이 틀을 프롬프트로 명시하는 것이 위협 도출의 재현성과 완전성을 높이는 방법이다.

## B4. Attack Tree / Attack Path

공격자가 하나의 목표(예: "Engine Control 장악")를 달성하기 위해 거쳐야 하는 여러 단계와 대안
경로를 트리 구조로 표현한 것이다. 뿌리(목표)에서 잎(구체적 진입점)까지의 한 경로가 하나의
"Attack Path"다. STRIDE(B3)가 "어떤 종류의 위협이 있는가"를 넓게 훑는다면, Attack Tree는 "그
위협이 실제로 실행되려면 어떤 순서로 무엇을 거쳐야 하는가"를 깊게 추적한다.

**왜 중요한가**: Model 01의 출력이 "위협 목록"에 그치지 않고 "공격 경로"까지 나와야 방어
아키텍처(어느 지점을 막을지)를 설계할 수 있다. STRIDE로 넓게 찾고 Attack Tree로 구체화하는 것이
`exp_004`의 기본 틀이다.

## B5. IEC 62443과 Zone & Conduit

`IEC 62443`은 산업제어시스템(ICS/OT) 보안을 위한 국제 표준 시리즈다. 이 표준의 핵심 개념이
**Zone(구역)**과 **Conduit(도관)**이다.

- **Zone**: 동일한 수준의 보안 요구사항을 갖는 자산들의 논리적 그룹 (예: "항해 장비 Zone",
  "엔진 제어 Zone")
- **Conduit**: Zone과 Zone 사이의 통신 경로. 이 경로에 방화벽 등 통제를 배치해 한 Zone이
  뚫려도 다른 Zone으로 피해가 번지지 않게 한다.

`IACS UR E26`이 요구하는 "선박 네트워크 분리"가 바로 이 Zone & Conduit 모델을 선박에 적용한
것이다.

**왜 중요한가**: Model 01의 "Defense Architecture Generator"가 최종적으로 출력해야 하는 것이 바로
"이 자산들을 어떤 Zone으로 나누고, Zone 사이 Conduit에 어떤 통제를 둘 것인가"다. 다만 이 분리를
과하게 하면 실제 항해장비 간 필수 통신(NMEA 데이터 등)이 끊어지는 부작용(Over-blocking)이 생길 수
있다는 점도 함께 고려해야 한다 — 이는 테스트베드가 갖춰진 뒤(Phase 5) 실증해야 확인 가능한
부분이다.

## B6. 선박 통신 프로토콜 (NMEA 0183/2000, IEC 61162-450)

`NMEA 0183`과 후속 표준인 `NMEA 2000`은 GPS, RADAR, ECDIS, AIS 같은 항해 장비들이 위치·항로
같은 데이터를 주고받을 때 쓰는 표준 메시지 형식이다. `IEC 61162-450`은 이 NMEA 데이터를 이더넷
네트워크 위에서 주고받기 위한 표준이다.

**왜 중요한가**: Threat Modeling(B3, B4)이 다루는 "자산 간 연결 구조"가 실제로는 이 프로토콜들
위에서 흐르는 데이터다. 이 프로토콜을 모르면 "어느 연결이 끊어지면 안 되는 필수 통신인지",
"어디에 스푸핑/변조가 실제로 가능한지"를 구체적으로 판단할 수 없다 — STRIDE 체크리스트를 채우는
것과 그 위협이 실제로 이 프로토콜의 어떤 취약점 때문에 가능한지 설명하는 것은 다른 수준의 깊이다.

## B7. LLM 에이전트 아키텍처 (Planner / Tool Interface / Executor / Evaluator / Memory)

단일 질의응답을 넘어, LLM이 여러 단계에 걸쳐 도구(tool)를 사용하며 작업을 수행하도록 만든
구조다. 일반적으로 아래 역할로 나눈다.

- **Planner**: 큰 목표를 실행 가능한 작업 단위로 분해
- **Tool Interface**: 외부 도구(스캐너, API, 파일시스템 등)를 LLM이 호출할 수 있는 표준화된
  형태로 노출 — 이때 LLM이 "이 도구를 이 인자로 불러라"를 구조화된 형식으로 출력하는 것을
  **tool-calling(function calling)**이라 한다
- **Executor**: 실제로 도구를 실행
- **Evaluator**: 실행 결과가 기대한 것과 맞는지 판정
- **Memory**: 과거 실행 결과를 다음 계획에 반영할 수 있도록 축적

**왜 중요한가**: Model 02가 이 구조 그대로다. `exp_005_agent`의 현재 단계(스모크 테스트)는
이 다섯 요소 중 Planner→Tool Interface→Executor까지의 최소 루프가 승인된 샌드박스에서 굴러가는지
확인하는 것이고, Evaluator·Memory를 포함한 전체 closed-loop는 Model 01이 Phase 4를 통과하고
테스트베드가 갖춰진 뒤(Phase 5)의 일이다.

- Related: `00.docs/02.architecture/model_02_architecture.md`, `04.model_02/CLAUDE.md`

## B8. Fine-tuning은 왜 아직 안 하는가

모델을 도메인에 맞게 개선하는 방법에는 비용/난이도가 다른 여러 단계가 있다.

1. **Prompt engineering** — 모델 가중치는 그대로 두고 지시문·형식만 바꾼다. 가장 싸고 빠르다.
2. **RAG(B1)** — 모델 가중치는 그대로 두고 검색 결과를 컨텍스트로 추가한다. 학습 없이 지식을
   확장할 수 있다.
3. **Fine-tuning** — 실제로 모델 가중치를 도메인 데이터로 재학습한다. 비용이 크고, 잘못하면
   기존 능력을 훼손(catastrophic forgetting)할 수 있다.
4. **선호도 최적화/강화학습** — fine-tuning보다도 더 정교하고 비싼 방법. 장기 과제.

**왜 중요한가**: root `CLAUDE.md`가 "평가로 정당화되기 전까지 fine-tuning을 시작하지 말라"고
못박은 이유가 여기 있다. 지금까지의 모든 문제(A3~A6)가 prompt engineering이나 RAG로 해결
가능한지조차 아직 다 확인되지 않았다 — 이걸 건너뛰고 fine-tuning부터 하면, 어떤 개선이 어떤
개입 때문인지 구분할 수 없게 된다. 또한 로컬 GPU(RTX 4070 SUPER 12GB)로는 14B 모델의
fine-tuning조차 현실적으로 어렵다(32B인 Model 02는 더더욱).

## B9. Closed-loop 검증 / 테스트베드

Model 01이 "이 방어책을 적용하면 이 공격을 막을 수 있다"고 예측하면, 그 예측을 말로만 남기지
않고 실제(또는 시뮬레이션된) 환경에 적용해 진짜로 막히는지 실행해보고, 그 결과를 다시 Model 01의
지식/판단에 반영하는 순환 구조다. 보안 공학에서 일반적으로 쓰이는 "설계 → 검증 → 피드백" 루프를
AI 파이프라인에 적용한 것이라고 보면 된다.

**왜 중요한가**: 산업계 솔루션의 가장 큰 약점이 "진짜 장비로 실증할 기회가 거의 없다"는 것이었다
(대부분 엑셀/이론 시나리오로 평가 종료). 항해 장비 실물 경험이 있는 사람만 설계할 수 있는 이
closed-loop가 이 연구의 독창성 근거 중 하나다. 다만 테스트베드가 없는 지금은 실행 불가능한
단계이고, Model 02의 현재 범위는 B7에서 설명한 스모크 테스트로 제한된다.

## B10. MASS (Maritime Autonomous Surface Ships) — 박사 단계 후보

IMO가 정의한 자율운항선박 분류 체계로, 사람이 승선해 직접 조작하는 정도에 따라 여러 등급(원격
제어부터 완전 자율까지)으로 나뉜다. 자율/원격 제어 루프 자체가 사람이 개입해 이상을 즉시 알아챌
수 없는 새로운 공격 표면이 된다.

**왜 중요한가**: `research_question.md`의 Evolution Path에서 언급한 박사 단계 확장 후보다. 지금
검증 중인 "규정 기반 위협 모델링 + 실증 검증" 방법론이 유효하다고 확인되면, 그 방법론을 사람이
개입하지 않는 자율 의사결정 시스템의 보안 검증으로 일반화하는 것이 다음 단계의 논리다. 지금
당장 깊이 알아야 할 개념은 아니고, 방향 감각만 잡아두면 된다.

# C. 빠른 용어 사전

| 용어 | 한 줄 정의 |
|---|---|
| RAG | 질의 시점에 외부 문서를 검색해 근거로 주입하는 방식 |
| Grounding | 모델의 모든 주장에 검증 가능한 출처를 강제로 연결하는 것 |
| Hallucination | 그럴듯하지만 사실이 아닌 내용을 생성하는 현상 |
| STRIDE | 6가지 위협 유형 체크리스트(Spoofing/Tampering/Repudiation/정보노출/서비스거부/권한상승) |
| Attack Tree | 공격 목표 달성까지의 단계·경로를 트리로 표현한 것 |
| Zone & Conduit | IEC 62443의 네트워크 분리 개념 — 자산 그룹(Zone)과 그 사이 통신로(Conduit) |
| IACS UR E26/E27 | 국제선급협회가 정한 선박 전체/개별 장비의 사이버 복원력 요구사항 |
| NMEA 0183/2000 | 항해 장비 간 위치·항로 데이터 교환 표준 |
| Tool-calling | LLM이 외부 도구 호출을 구조화된 형식으로 출력하는 기능 |
| Fine-tuning | 모델 가중치 자체를 도메인 데이터로 재학습하는 것 (이 프로젝트에서는 아직 보류) |
| Closed-loop 검증 | AI의 예측을 실제/시뮬레이션 환경에 적용해 맞는지 확인하고 피드백하는 순환 구조 |
| MASS | 자율운항선박(Maritime Autonomous Surface Ships) |
