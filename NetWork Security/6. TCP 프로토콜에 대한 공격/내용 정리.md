# 1. TCP 프로토콜
## 1) 개요
- TCP(Transmission Control Protocol) - 인터넷 프로토콜 그룹의 핵심 프로토콜
- 안정적이고 정렬된 통신 채널을 제공
- 신뢰성과 순서화된 통신을 달성하기 위해 TCP는 연결을 유지하기 위해 통신의 양쪽 종단(end)이 필요
- 연결하는 파이프는 기본적으로 보안 매커니즘이 적용되지 않아, 보호되지 X 
	-> 공격자가 연결을 도청하고 가짜 데이터를 연결에 주입하고 연결을 끊고 연결을 하이재킹할 수 있음
## 2) TCP 프로토콜 동작 방식
- 이해를 위한 코드 -> Source code 분석 참조
### (데이터 전송 : 내부)
- 연결이 설정되면 운영체제는 데이터 전송(전송 버퍼)과 데이터 수신(수신 버퍼)을 위해 각 종단에 두 개의 버퍼를 할당
- 응용 프로그램이 데이터를 보낼 때 패킷을 직접 구성하지 않음 => 데이터를 TCP 전송 버퍼에 넣음
- 운영체제 내의 TCP 코드는 데이터를 보낼 시기를 결정
	- 이때, 작은 데이터가 포함된 패킷을 보내 네트워크 대역폭을 낭비하는 것을 방지하기 위해 TCP는 정해진 시간동안 기다리거나, 데이터가 IP 단편화를 일으키지 않고 하나의 패킷에 넣기 충분할 때까지 기다림
- 송신 버퍼의 각 옥텟에는 연관된 순서 번호가 있음 => TCP 헤더에 페이로드의 첫번째 옥텟에 필드
	-> 수신자 측에서 패킷이 도착하면 수신 버퍼내의 올바른 위치에 데이터를 배치
- 성능을 위해 TCP는 데이터가 도착하는 즉시 응용 프로그램의 차단을 해제하지 않고, 충분한 데이터가 있거나 충분한 대기 시간이 경과할 때까지 기다림
- 수신자는 데이터가 수신되었음을 송신자에게 알림 => 확인 응답 패킷을 전송 => 수신이 예상되는 다음 순서번호를 송신
	=> 송신자가 일정 시간내에 확인응답을 받지 못하면 데이터가 손실된것으로 간주하고 데이터를 다시 보냄
# 2. 공격
## (1) SYN 플러딩 공격
- TCP 연결이 설정되는 기간, 즉 TCP 3-way handshake protocol이 대상
### 재전송(Retranmission)
- 최종 ACK 패킷이 오지 않으면 서버는 SYN+ACK 패킷을 여러번 재전송
- 최종 ACK 패킷이 오지 않으면 SYN 큐에 저장된 레코드가 결국 시간 초과되어 폐기됨
```bash
sysctl net.ipv4.tcp_synack_retries

// change the value to 10
sudo sysctl -w net.ipv4.tcp_synack_retries=10
```
-> 커널의 매개변수의 값을 읽고 설정이 가능
### SYN 큐의 크기
- SYN 큐에 저장할 수 있는 절반-개방 연결 수는 큐의 크기에 따라 달라지며, 큐의 크기는 시스템의 메모리 양에 따라 운영체제에서 결정됨
- 시스템에 메모리가 많을수록 SYN 큐의 크기가 커짐
```bash
sysctl net.ipv4.tcp_max_syn_backlog // find queue size

// change the queue size to 128
sudo sysctl -w net.ipv4.tcp_max_syn_backlog=128
```
### 공격 원리
- 3-way handshake가 완료되기전 모든 half-open connection을 큐에 저장하는데, 이 Queue를 빠르게 채운다면, 연결에 대한 레코드를 저장할 공간이 없으므로, 서버는 새로운 SYN 패킷을 수락할 수 X
	-> 서버의 CPU와 대역폭이 아직 용량에 도달하지 않았음에도, 더 이상 연결 X ==> DOS 공격

- 3-Way Handshake  Protocol이 ACK 패킷을 받는 단계를 완료하지 않음

### 대응책
#### SYN 쿠키 매커니즘
- 일반적으로 초기 TCP 순서 번호는 서버에서 무작위로 생성되지만 SYN 쿠키 메커니즘은 유용한 정보를 인코딩하기 위해 순서 번호를 이용한다.
- 서버는 SYN 패킷을 수신한 후 서버에만 알려진 비밀 키를 사용하여 IP 주소, 포트 번호와 순서 번호를 포함하는 패킷의 정보에서 키있는 해시(keyed hash)를 계산
- 이 해시 값 H는 클라이언트로 다시 전송되는 서버의 SYN+ACK 패킷에 배치된 초기 순서 번호로 사용한다
- 이 H가 SYN 쿠키이다
	-> 클라이언트가 공격자인 경우, 패킷이 공격자에게 도달하지 않음(SYN 플러딩 공격에서 클라이언트의 IP 주소는 가짜)
	-> 클라이언트가 공격자가 아닌 경우, 패킷을 받고 확인응답 필드에 값 H+1이 포함된 ACK 패킷을 다시 보냄
	 => 서버는 이 ACK 패킷을 수신하면 패킷의 정보를 기반으로 쿠키를 재계산하여 ACK 필드 내의 순서번호가 유효한지 여부를 확인할 수 있음
	- 즉, 이 확인 단계로 ACK 플러딩을 방지하고, ACK 패킷이 이전 SYN+ACK 패킷의 결과인지 확인
		-> 공격자는 쿠키 계산에 사용된 비밀을 모르기에 유효한 쿠키를 쉽게 위조할 수 없음
## (2) TCP 리셋 공격
### 동작 방식
- 아이디어
	- A와 B의 연결을 끊기위해, TCP RST 패킷을 스푸핑
- 전제 조건
	- 스푸핑된 패킷의 Dest' IP Address, Dest' Port, Source IP Address, Source Port의 필드는 연결에서 사용하는 필드와 동일해야함
	- 스푸핑된 패킷의 순서번호가 정확해야됨 -> 그렇지 않으면, 패킷이 폐기됨
### 공격의 동작
- Source code 분석에서
- Telnet이나, SSH나 동일하게 공격이 적용
	-> 암호화된 TCP 연결(SSH) 네트워크 계층이 아닌 전송 계층에서 암호화를 수행
	=> 헤더가 아닌 TCP 패킷의 데이터만 암호화 
	- 즉, 공격은 헤더 부분만 스푸핑하면 되고 RST 패킷에는 데이터가 필요하지 않기에
